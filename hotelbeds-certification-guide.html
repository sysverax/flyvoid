Hotelbeds (HBX Group) Certification Guide

Everything needed to prepare, self-test, and request certification for the Hotel Booking API — with request bodies and JSON schemas ready to drop into Postman.

iOverview

Certification confirms your integration calls the Hotel API in the correct order, displays all mandatory information correctly, generates a compliant voucher, and behaves correctly on a real live booking. Reference: official certification process doc.

Contact for certification requests and questions: apitude@hotelbeds.com

iPostman variables used in this guide

All requests below use these collection/environment variables — set them once in Postman and every request in this guide will work as-is.

VariableExample valueNotes
{{baseURL}}https://api.test.hotelbeds.comSwitch to https://api.hotelbeds.com only after certification, for live keys
{{version}}1.0Applies to hotel-api and hotel-content-api
{{hotelbeds-api-key}}your test Api-keySent as Api-key header
{{hotebeds-x-signature}}computed per-requestSHA-256 of apiKey + secret + UTC epoch seconds. Should be a Postman pre-request script so it's fresh on every send.
Important: the X-Signature must be regenerated for every request (it embeds the current timestamp). If you hardcode it, requests will start failing within ~30 seconds.

iCertification roadmap

  1. Read the best practices doc and build against the test environment

    Implement Availability → CheckRate (conditional) → Booking in the correct order, with GZIP compression enabled on requests.

  2. Self-test every endpoint below

    Use the curl commands and schemas in this guide to confirm each call works and returns the shape you expect before contacting Hotelbeds.

  3. Implement voucher generation

    Assemble the mandatory voucher fields (Section 7) from the Booking detail response plus Content API data.

  4. Email apitude@hotelbeds.com to request certification

    Include your workflow, commercial exclusions, test URL/credentials, and any language notes (see "Requesting certification" section).

  5. Pass the 5-area review

    Technical (GZIP/config), Workflow (call order/batching), Availability–CheckRate–Confirmation (data display + rules), Voucher, and Content.

  6. Receive live API keys

    Point {{baseURL}} at the live host once issued.

  7. Perform one real live booking, then cancel it

    6 months out, 2 adults/2 children, non-NRF rate. Send Hotelbeds the voucher and price, coordinate cancellation timing with them, then cancel.

  8. Confirm non-breaking-change tolerance

    Your integration must not break on new fields, new optional params, or reordered response properties.

0Status check GET

Confirms your Api-key and X-Signature are valid before you test anything else.

curl
curl --location --request GET '{{baseURL}}/hotel-api/{{version}}/status' \
--header 'Api-key: {{hotelbeds-api-key}}' \
--header 'X-Signature: {{hotebeds-x-signature}}' \
--header 'Accept: application/json' \
--header 'Accept-Encoding: gzip'

1Availability POST Batch all rooms, ≤2000 hotels

First call in the workflow. Request every hotel you can (up to 2000) and every room needed for the booking in a single call — do not split rooms of the same booking across multiple Availability calls.

curl
curl --location --request POST '{{baseURL}}/hotel-api/{{version}}/hotels' \
--header 'Api-key: {{hotelbeds-api-key}}' \
--header 'X-Signature: {{hotebeds-x-signature}}' \
--header 'Accept: application/json' \
--header 'Accept-Encoding: gzip' \
--header 'Content-Type: application/json' \
--data-raw '{
    "sourceMarket": "UK",
    "stay": { "checkIn": "2026-06-15", "checkOut": "2026-06-16" },
    "occupancies": [
        { "rooms": 1, "adults": 2, "children": 0 },
        {
            "rooms": 1, "adults": 3, "children": 1,
            "paxes": [ { "type": "CH", "age": 7 } ]
        }
    ],
    "hotels": { "hotel": [1067, 1070, 1074] },
    "filter": { "maxHotels": 50, "minRate": 0, "maxRate": 1000 }
}'

Key rule from the Availability response

Every rate has a rateType. Only call CheckRate when it equals RECHECK — otherwise book directly with the returned rateKey.

"rates": [
  {
    "rateKey": "20260615|20260616|W|1|1067|DBT.SU|CG-BAR17HB|HB||1~2~0||...",
    "rateClass": "NOR",
    "rateType": "BOOKABLE"
  }
]

2CheckRate POST Only if rateType=RECHECK, ≤10 keys/call

Revalidates price and availability for a rateKey immediately before booking. Group up to 10 rateKeys in one call rather than calling repeatedly.

curl
curl --location --request POST '{{baseURL}}/hotel-api/{{version}}/checkrates' \
--header 'Api-key: {{hotelbeds-api-key}}' \
--header 'X-Signature: {{hotebeds-x-signature}}' \
--header 'Accept: application/json' \
--header 'Accept-Encoding: gzip' \
--header 'Content-Type: application/json' \
--data-raw '{
    "rooms": [
        { "rateKey": "PASTE_RATEKEY_1_FROM_AVAILABILITY" },
        { "rateKey": "PASTE_RATEKEY_2_FROM_AVAILABILITY" }
    ]
}'

3Booking confirm POST Min. 60s timeout (use 65s buffer)

Final step of the workflow. Do not call Availability or CheckRate again immediately before this — use the rateKey you already have.

curl
curl --location --request POST '{{baseURL}}/hotel-api/{{version}}/bookings' \
--max-time 65 \
--header 'Api-key: {{hotelbeds-api-key}}' \
--header 'X-Signature: {{hotebeds-x-signature}}' \
--header 'Accept: application/json' \
--header 'Accept-Encoding: gzip' \
--header 'Content-Type: application/json' \
--data-raw '{
    "holder": { "name": "John", "surname": "Smith" },
    "rooms": [
        {
            "rateKey": "PASTE_FINAL_RATEKEY_HERE",
            "paxes": [
                { "roomId": 1, "type": "AD", "name": "John", "surname": "Smith" },
                { "roomId": 1, "type": "AD", "name": "Jane", "surname": "Smith" }
            ]
        }
    ],
    "clientReference": "your-internal-ref-001",
    "remark": "Certification test booking",
    "tolerance": 2.00
}'

schema
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "BookingConfirmRequest",
  "type": "object",
  "required": ["holder", "rooms"],
  "properties": {
    "holder": {
      "type": "object",
      "required": ["name", "surname"],
      "properties": {
        "name": { "type": "string" },
        "surname": { "type": "string" }
      }
    },
    "rooms": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["rateKey", "paxes"],
        "properties": {
          "rateKey": { "type": "string" },
          "paxes": {
            "type": "array",
            "items": {
              "type": "object",
              "required": ["roomId", "type", "name", "surname"],
              "properties": {
                "roomId": { "type": "integer" },
                "type": { "type": "string", "enum": ["AD", "CH"] },
                "age": { "type": "integer" },
                "name": { "type": "string" },
                "surname": { "type": "string" }
              }
            }
          }
        }
      }
    },
    "clientReference": { "type": "string" },
    "remark": { "type": "string" },
    "tolerance": { "type": "number", "description": "Allowed price variance vs the last checked rate" }

Timeout: Hotelbeds requires your system to wait at least 60 seconds for the Booking Confirmation response before treating it as failed/timed out. Using 65s gives a safety margin.

7Voucher assembly Not an endpoint — built from Booking detail + Content API

Every confirmed booking must produce a voucher for the end client. Build it from the Booking detail response, enriched with Content API hotel data.

Hotel information

  • Hotel name mandatory
  • Hotel address mandatory
  • Hotel category recommended
  • Destination name recommended
  • Hotel phone number recommended

Passenger information (all mandatory)

  • Holder name — must be the lead passenger from the booking request
  • At least one pax name per room (holder's name is sufficient for single-room bookings)
  • Children's ages, if children are present

Booking information

  • Hotelbeds booking reference mandatory
  • Agency reference recommended
  • Check-in / check-out dates mandatory
  • Room type mandatory
  • Board type mandatory
  • Rate comments, if applicable mandatory

Payment disclosure mandatory wording

Do not display the reservation price on the voucher. Instead show:

"Payable through XXX, acting as agent for the service operating company,
details of which can be provided upon request. VAT: YYY  Reference: ZZZ"

Where XXX = supplier name (supplier tag), YYY = VAT number (supplier tag), ZZZ = booking reference.

8Content API GET — category, images, facilities, descriptions

Not mandatory to use, but if you do, certification checks it's implemented correctly. Cache this data locally and refresh at least weekly.

curl
curl --location --request GET '{{baseURL}}/hotel-content-api/{{version}}/hotels/1067/details?language=ENG&useSecondaryLanguage=false' \
--header 'Api-key: {{hotelbeds-api-key}}' \
--header 'X-Signature: {{hotebeds-x-signature}}' \
--header 'Accept: application/json' \
--header 'Accept-Encoding: gzip'

What certification checks here

  • Category types shown (stars, keys, apart-hotel ratings) and values
  • Images displayed, correctly matched to the right hotel, and in reasonable quantity
  • Facilities shown, including paid (indFee) and "mandatory-reported" (indYesOrNo) facilities
  • Hotel description, contract remarks, room types, board types, points of interest

Facility response example

{
  "facilityCode": 330,
  "facilityGroupCode": 70,
  "description": { "content": "Garage" },
  "order": 1,
  "indFee": true,
  "indYesOrNo": true
}

indFee: true = paid facility. indYesOrNo present = a "mandatory-reported" facility, meaning Hotelbeds always asks the hotel to confirm whether it has this facility or not (the value tells you which).

iRequesting certification

Once every endpoint above works as expected and your voucher is compliant, email apitude@hotelbeds.com with:

  • Your integration workflow (per distribution channel, if more than one)
  • Any commercial exclusions (destinations, room types, board types, hotels deliberately omitted)
  • The certification test URL
  • Username/password, if your system requires login to view the integration
  • Payment information, if applicable
  • A language guide, if your UI isn't in a common language
  • How to isolate HBX Group product, if you integrate multiple suppliers
  • Any other context relevant to reviewing your integration

iGoing live

  1. Receive live Api-key and secret

    Point {{baseURL}} at the live host and regenerate your X-Signature against the live secret.

  2. Make one real booking

    Dates 6 months in advance, 2 adults/2 children, a non-NRF rate (NRF = non-refundable, carries cancellation fees).

  3. Send Hotelbeds the voucher and price

    For their final verification.

  4. Cancel the booking

    Confirm timing with Hotelbeds first — otherwise you may be charged.

  5. Confirm non-breaking-change tolerance

    New response fields, new endpoints, new optional request params, reordered response properties, and changed string lengths/formats should never break your integration.

Any action on the live environment is real — the hotel is informed and cancellation fees apply if the rate carries them. Never test with an NRF or fee-bearing rate.
